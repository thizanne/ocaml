1. Setup: build the compiler, learn to spy on it

Check out the feature branch and build (the tree self-bootstraps; the first build takes a few minutes):

git checkout range_patterns_v8 && ./configure && make -j

The single most useful skill for this tutorial: the compiler will show you its intermediate representations. Because you are running the in-tree compiler, point it at the in-tree stdlib:

alias oc='./ocamlc.opt -nostdlib -I ./stdlib'
oc -dparsetree -c ex.ml   # what the parser produced
oc -dtypedtree -c ex.ml   # what the type checker produced
oc -dlambda    -c ex.ml   # what pattern-match compilation produced

You will use these three flags constantly. Everything the series does is visible through one of them.

2. Background: the life of a match

Before reading any diff, you need the map. A match expression crosses five stations:

 parser.mly ──▶ typecore.ml ──▶ parmatch.ml ──▶ translcore.ml ──▶ matching.ml
 (Parsetree)    (Typedtree)     (warnings)      (elaboration)     (Lambda IR)

The canonical description of this pipeline is the toplevel comment of lambda/matching.ml (added by PR #3, which this series is stacked on). Here it is, typeset for reading — go through it now; the rest of this tutorial adds worked examples to it.

“Pattern matching in the compiler: the pipeline”
typeset from the toplevel comment of lambda/matching.ml, which remains the authoritative copy

This section is an overview of how pattern matching is handled across the compiler, from parsing to code generation; the headers of typing/typecore.ml, typing/parmatch.ml and typing/patterns.mli point here.

parser.mly --> typecore.ml --> parmatch.ml --> translcore.ml --> this file
(Parsetree)    (Typedtree)     (warnings)      (elaboration)     (Lambda)

Parsing

Patterns enter the compiler as the Parsetree.Ppat_* nodes built by parsing/parser.mly: constants, constructors, or-patterns (Ppat_or), aliases (Ppat_alias), etc. Character ranges such as 'a'..'z' are parsed as Ppat_interval; only character bounds survive type checking, which expands the range into an or-pattern enumerating every character in between.

Type checking

Typecore.type_pat (recursive worker: type_pat_aux) checks a parsetree pattern against an expected type and returns a typedtree pattern carrying its type and environment. The typedtree distinguishes “value” patterns, which match values, from “computation” patterns, which also match the effect of a computation (Tpat_value, Tpat_exception); type_pat receives the expected category as a GADT tag (see the comment above Typecore.pure). Typedtree.split_pattern then separates a computation pattern into its value and exception parts, so that the two halves of a match are checked and compiled separately.

Warnings

Typecore.type_cases runs the match analyses of typing/parmatch.ml through Parmatch.check_partial and check_unused: exhaustiveness is computed on the value clauses, redundancy on value and exception clauses separately. The algorithms follow Maranget, “Warnings for pattern matching” (JFP 17(3), 2007). The central notion is the usefulness of a row with respect to a matrix (satisfiable, every_satisfiables): exhaustiveness is usefulness of a wildcard row (exhaust), and a clause is redundant when it is not useful with respect to the previous unguarded ones (le_pat and get_mins prune the matrix). Counter-examples are built by full_match and build_other, and — as they may be ill-typed in the presence of GADTs — refined by Typecore.check_counter_example_pat (see the comment around counter_example_checking_info). The resulting Partial/Total verdict is stored in the typedtree and reused here.

Pattern views

The analyses and this module do not consume raw typedtree patterns, whose head can be a variable, an alias or an or-pattern as well as an actual shape: if every pattern match over patterns handled those three administrative cases itself, forgetting one would be a silent bug. typing/patterns.ml instead encodes in the type what may appear at a pattern's head. General re-expresses the typedtree as a polymorphic variant; Half_simple (General.strip_vars) guarantees that no variable or alias remains at the head, turning them into bindings on the clause's action; Simple further excludes or-patterns at the head, which the precompilation pass of this module splits into separate rows. The constraint bears on the head only: sub-patterns are arbitrary, so Some (1 | 2) is simple while (1 | 2) is only half-simple. Finally, the Head module isolates the head constructor alone: Head.deconstruct returns a pattern's head and its immediate sub-patterns, and Head.arity the number of those (a constant has arity 0, Some has arity 1, a tuple its width) — the currency of matrix specialization throughout the analyses and this module.

Elaboration

lambda/translcore.ml invokes this module through one entry point per elaboration site (see matching.mli): for_function, for_let, for_multiple_match, for_trywith, for_handler, for_tupled_function, for_optional_arg_default. Translcore also compiles when guards (transl_guard) to Lifthenelse (cond, body, staticfail); compile_match uses patch_guarded to plug the rest of the match in place of the staticfail placeholder.

Code generation

This module compiles matches to Lambda following the scheme described in the next section. Columns of integer-like constants (ints, chars, constructor and variant tags) are dispatched through call_switcher and lambda/switch.ml, which compiles a generic switch into a mixture of if-tests and jump tables. The Context, Default_environment and Jumps modules below track, per program point, the values that can reach it and the live exits; the row specializer matcher deliberately over-approximates “may match”. Finally, the Partial/Total verdict from typing drives failure handling (toplevel_handler, failure_handler): a Partial match is wrapped in a static catch whose handler raises Match_failure (or re-raises, for try...with); if typing said Total but compilation degrades to Partial, warning Degraded_to_partial_match is emitted, and -safer-matching (Clflags.safer_matching) forces Partial everywhere.

2.1 Station 1 — the parser

The parser turns text into Parsetree.Ppat_* nodes and does no thinking. Try it:

echo 'let f x = match x with 0 .. 10 -> 1 | _ -> 2' > ex.ml
oc -dparsetree -c ex.ml
pattern (ex.ml[1,0+23]..[1,0+30])
  Ppat_interval
  constant (ex.ml[1,0+23]..[1,0+24])
    PConst_int (0,None)
  constant (ex.ml[1,0+28]..[1,0+30])
    PConst_int (10,None)

Surprise #1: Ppat_interval already existed before this series — it is how char ranges 'a'..'z' parse, and the grammar always accepted any constants as bounds. Rejecting non-char bounds was the type checker's job. So the series needs no parser change.

2.2 Station 2 — the type checker

Typecore.type_pat checks a parsetree pattern against an expected type and produces a typedtree pattern (every node now carries its type and environment). On trunk, this is where char ranges get rewritten: 'a'..'c' becomes the or-pattern 'a'|'b'|'c'. See for yourself:

echo "let g c = match c with 'a'..'c' -> 1 | _ -> 2" > ex.ml
oc -dtypedtree -c ex.ml
Tpat_or
  Tpat_constant Const_char 61   (* 0x61 = 'a' *)
  Tpat_or
    Tpat_constant Const_char 62
    Tpat_constant Const_char 63 ...

That trick obviously cannot scale to min_int .. max_int — which is the whole reason this series exists.

2.3 Station 3 — the warnings analyses

typing/parmatch.ml answers two questions about a typed match: is it exhaustive (warning 8)? is any clause useless (warning 11)? It is driven from Typecore.type_cases via Parmatch.check_partial and check_unused. The algorithms come from Maranget's “Warnings for pattern matching” (JFP 2007). Section 3 below gives you the core idea.

2.4 Stations 4–5 — elaboration and compilation

lambda/translcore.ml calls into lambda/matching.ml (entry points for_function, for_let, for_trywith…), which compiles the match to the untyped Lambda IR, following Le Fessant–Maranget (ICFP 2001). Integer dispatch ultimately goes through lambda/switch.ml, which decides between if-trees and jump tables. You will read real Lambda output in section 5.

3. Background: pattern matrices, the one idea behind everything

Both the warnings analyses and the compiler see a match as a matrix: one row per clause, one column per value being matched. For

match x, y with
| 0, _     -> A
| _, true  -> B
| _, _     -> C

the matrix is:

  row 1:   0      _
  row 2:   _      true
  row 3:   _      _

All algorithms walk this matrix by specialization: pick the first column, pick a head (a top-level constructor, like the constant 0 or true), and build the sub-matrix of rows that could match a value starting with that head, with the first column consumed. A wildcard row survives every specialization. There is also the default matrix: rows that match values whose head is none of the listed ones.

Two crown jewels are built from this single operation:

  • Usefulness (Parmatch.satisfiable): is there a value that matches row q but none of the rows above it? A match is exhaustive iff a wildcard row is not useful after all clauses (exhaust even builds the witness — that is the counter-example the compiler prints). A clause is redundant iff it is not useful after the previous ones.
  • Compilation (Matching.compile_match): specialize on each head of the first column, compile each sub-matrix recursively, emit a dispatch (switch / if-chain) over the heads, and chain the fall-through cases with static exits (catch … with (exit n) … in Lambda).
The key invariant
For the compilation-by-specialization strategy to be sound, the heads grouped into one dispatch must be pairwise disjoint or equal — a value must not be able to match two different cells of the same dispatch. Trunk maintains this invariant in split_no_or (see its comment in matching.ml): constants are naturally pairwise disjoint-or-equal, and the one pre-existing exception — extension constructors, which may alias through rebinding — is handled by refusing to group them (can_group) and chaining the groups with exits instead. Keep this invariant in mind: intervals will break it, and the most important commit of the series restores it.

4. What the series adds, from 30,000 feet

As a user you already know the feature: lo .. hi now works for int, int32, int64, nativeint, matching inclusively, first match wins, bounds in either order. Behind the scenes, one new typedtree constructor carries the range through the compiler without enumeration:

echo 'let h x = match x with 5 .. 10 -> 1 | _ -> 2' > ex.ml
oc -dtypedtree -c ex.ml | grep interval
Tpat_interval Const_int 5..Const_int 10

Everything else in the series is the consequence of that one node existing: every layer that pattern-matches on patterns must handle it, the warnings analyses must reason about ranges instead of counting constants, and the compiler must dispatch on ranges soundly — including when they overlap. For contrast, this is what any pre-series compiler says (captured with released ocamlc 5.3; trunk's message is identical):

Error: Only character intervals are supported in patterns.

5. The sixteen commits, one by one

Get the list (hashes will differ if the branch was rebased; use the titles):

git log --reverse --oneline patmatch_docs..range_patterns_v8

For each commit below: read the summary here, then git show <hash> and look for the named functions. The series is bisectable — every commit builds and passes its own tests, so you can git checkout any of them and poke at the compiler it builds.

Commit 1 — Add tests for interval pattern matching

Pure test file (exhaustiveness_interval.ml), written as expect tests: source followed by the compiler output frozen in the file. The trick to understand: at this commit, every integer-interval block expects the trunk error. Later commits update these expectations as behavior changes — so each subsequent diff shows you its own effect in the tests. When reading commits 3–10, always scroll to the test-file part of the diff last: it is the behavioral summary.

Commit 2 — Add Tpat_interval to typed tree infrastructure

Adds the constructor Tpat_interval : constant * constant to typing/typedtree.mli — read its doc comment, it states the invariant (strictly ordered bounds; equal bounds collapse to a constant; chars never appear). Then it threads the constructor through every place that matches on patterns — starting with the pattern views described in the pipeline overview of section 2:

module Simple = struct
  type view = [
    | `Any
    | `Constant of constant
    | `Interval of constant * constant     (* <- added by this commit *)
    | `Tuple of (string option * pattern) list
    | ...
  ]
end

The same line lands in General.view and Head.desc; an interval, like a constant, has Head.arity 0 — matching it inspects the scrutinee but opens nothing further, which is why the additions to the generic iterators/mappers are all no-ops. Printers, untypeast and cmt output follow. Fourteen files, all mechanical, and all dead code: nothing produces the constructor yet. It must be one commit because the compiler builds with warnings-as-errors: adding a variant to the views forces every consumer — parmatch's analyses, matching.ml, the printers — to say what it does with an interval head, and a new constructor plus an unhandled match anywhere = broken build.

Commit 3 — Produce Tpat_interval for non-char integer intervals

The feature switch, in Typecore.type_pat_aux's Ppat_interval case. Read the new code top to bottom; it is self-contained:

  • get_bound converts each bound at its own location (so errors underline the offending bound, not the whole interval), rejects float/string with Invalid_interval, and unifies the bound's type with the expected type — which is what rejects 0l .. 100.
  • Bounds are sorted with Parmatch.const_compare (10 .. 0 ≡ 0 .. 10), a degenerate n .. n becomes Tpat_constant, chars keep the old or-expansion, and everything else becomes Tpat_interval.

From here until commit 10, typing and warnings work but code generation does not exist: compiling an interval match dies with a fatal error, and the expect tests record that honestly. This staging is deliberate.

Commits 4–6 — parmatch, in three layers

The warnings analyses learn ranges. The overview comment added at the top of parmatch's interval section (in commit 6) is your map. The trilogy:

CommitWhat it teaches parmatchKey functions
4 — head compatibility “can these two patterns match a common value?” Constant-in-interval is membership; interval-vs-interval is intersection. inside, intersects, compat, simple_match, all_coherent
5 — exhaustiveness a column of constants/intervals covers the type iff the sorted ranges run gaplessly from the type's minimum to its maximum; counter-examples come from the first gap. next_constant/prev_constant (successors that return None at type edges — no overflow), full_match, build_other, sorted_intervals_of_env
6 — subsumption & redundancy when does one pattern cover another (le_pat), what is their intersection (lub), and how or-pattern redundancy is deferred (every_satisfiables). le_pat, lub, every_satisfiables

Two things worth dwelling on. First, watch commit 5 work:

let gap x = match x with 0 .. 10 -> 1 | 12 .. 20 -> 2
Warning 8 [partial-match]: this pattern-matching is not exhaustive.
  Here is an example of a case that is not matched: 11

That “11” is build_other finding the first gap in the merged ranges. Second, in commit 6, read the long comment above le_pat's interval cases: the constant-vs-interval rule is deliberately asymmetric (a constant only subsumes an interval when the interval is that single point, while an interval subsumes a constant it contains). The comment explains how the “obvious” symmetric rule would corrupt get_mins, the matrix-pruning step used by both checks. This is the sort of invariant that is invisible until someone breaks it.

Commit 7 — Interval splitting for overlapping interval patterns

The analyses of commits 4–6 assume, in places, that two interval heads in a column are either equal or disjoint. Overlapping user code like 0 .. 10 / 5 .. 15 breaks that. This commit adds Maranget's disjointification: cut all the intervals of a column at each other's boundaries (0..4, 5..10, 11..15 in the example) so every original pattern becomes a union of pieces from one shared, disjoint set. Read the “Legend and function map” comment first — css is the pivotal data structure — then insert (which has a warning comment about a real bug the naïve recursion had), then split_pss_qs. It is called from satisfiable & co. with a one-shot flag so splitting cannot recurse forever. This machinery is what makes the union-redundancy warning work:

let union x = match x with 0 .. 10 -> 1 | 11 .. 20 -> 2 | 5 .. 15 -> 3 | _ -> 0
Warning 11 [redundant-case]: this match case is unused.   (on 5 .. 15)

Commit 8 — Interval heads in matcher and can_group

First contact with the compiler proper. Two small extensions in lambda/matching.ml: matcher (the row specializer used for reachability bookkeeping) learns interval heads — note it treats intersecting intervals as “may match”, an over-approximation its comment justifies — and can_group allows intervals to share a dispatch group with same-type constants. Innocent-looking; the next commit explains why can_group alone would be a trap.

Commit 9 — Enforce pairwise equal-or-disjoint keys when grouping intervals ★

The keystone; read it slowly, diff plus message plus the new comment in split_no_or. Recall the invariant from section 3. The subtlety: can_group only compares each candidate against the group's first head, which suffices when compatibility is transitive (e.g. Path.same for extension constructors). Equal-or-disjoint is not transitive: 200..300 and 250..350 are each disjoint from a first head 0..100, yet overlap each other. So collect now also checks each admitted constant/interval key against every key already in the group (keys_compatible); a clause whose key overlaps starts a new matrix, chained by an exit — first-match-wins by construction, the exact mechanism trunk already uses for extension constructors. The check costs nothing for interval-free matches (constants only scan the — empty — list of interval keys). Section 6 shows what went wrong historically without this.

Commit 10 — Interval code generation in matching.ml

Now that any single dispatch only ever sees pairwise disjoint ranges, code generation is pleasantly simple: divide_constant_interval groups clauses into cells keyed by exact bounds, and combine_constant_interval sorts cells by lower bound (order is free — disjoint!) and emits, per type and size:

let small x = match x with 0 .. 5 -> 1 | 6 .. 10 -> 2 | _ -> 0
let wide x = match x with 0 .. 1000 -> 1 | 1001 .. 2000 -> 2 | _ -> 0
let bsearch (x : int32) = match x with
  | 0l .. 100l -> 1 | 200l .. 300l -> 2 | 400l .. 500l -> 3 | 600l .. 700l -> 4
  | _ -> 0
(* small: jump-table/range machinery via lambda/switch.ml *)
(catch (if (>= x 6) (if (>= x 11) (exit 2) 2)
                    (if (>= x 0) 1 (exit 2))) with (2) 0)

(* wide: plain bound checks *)
(if (&& (<= 0 x) (<= x 1000)) 1
  (if (&& (<= 1001 x) (<= x 2000)) 2 0))

(* bsearch: binary search on lower bounds, then bound checks *)
(catch
  (if (Int32.< x 400l)
    (if (&& (Int32.<= 0l x) (Int32.<= x 100l)) 1
      (if (&& (Int32.<= 200l x) (Int32.<= x 300l)) 2 (exit 10)))
    (if (&& (Int32.<= 400l x) (Int32.<= x 500l)) 3
      (if (&& (Int32.<= 600l x) (Int32.<= x 700l)) 4 (exit 10))))
 with (10) 0)

Details to notice in the diff: small int intervals (< 256 wide) are expanded into individual switch entries and handed to call_switcher, which re-compresses them; a defensive check fatals if the disjointness invariant were ever violated; in a total match the last test of each chain is omitted; char never reaches this code as a real interval (only degenerate constants), because typecore still expands char ranges.

Commit 11 — Remove combine_constant's now-dead numeric branches

Housekeeping made possible by commit 10's dispatch change: only strings and floats still reach the old combine_constant, so its int/char/boxed-int branches are deleted. Pure deletion, no behavior change — verify by reading the new dispatch in do_compile_matching.

Commits 12–13 — runtime and -dlambda tests

intermatch.ml: ~50 functions run at test time on bytecode and native — boundaries (min_int32…), reversed and signed bounds, guards, tuples, records, lazy, nested constructors, duplicate keys, and a battery of overlap cases labelled with which rows overlap at each probed value (f27–f31, f32–f39). These encode the exact shapes of the two historical miscompilations of section 6. patmatch_interval.ml freezes the generated Lambda for each codegen shape above plus the overlap case, so any future change to dispatch is visible in review.

Commits 14–16 — manual, .mailmap, Changes

The reference-manual section (grammar rule, inclusive semantics, bounds-must-be-literals, an HTTP status example), and release notes. Note the manual documents that a space is currently needed in 0 .. 10 — lifting that is PR #2, a one-commit lexer change stacked on top.

6. The hard part: overlapping intervals (and two real miscompilations)

If you remember one thing, make it this section. Constants are pairwise disjoint; intervals are not. An earlier version of this series grouped overlapping intervals into a single dispatch keyed by exact bounds, and was wrong twice, silently, on both backends:

Bug 1 — lost fall-through. 
match x, y with
| 0 .. 10, true -> 1
| 5 .. 15, _    -> 2
| _             -> 4
(7, false) returned 4 instead of 2: the value entered the 0..10 cell, failed true, and fell to the match default — skipping the overlapping 5..15 row entirely. The cell partition had silently discarded the edge “row 2 may also match values of row 1's cell”.
Bug 2 — reordered dispatch. With a duplicated key (0..10 / 5..15 / 0..10), the grouping machinery orders cells by a key's last occurrence, so the dispatch tested 5..15 first and f 7 returned 2 instead of 1.

The fix is commit 9, and its shape is the deep lesson of this series: instead of patching the code generator to handle overlap (a “slow path” ordered chain — fragile, and historically wrong), the series restores the module's own invariant one level up: overlapping heads never share a dispatch. Groups are cut at overlap boundaries and chained with exits. Look at the compiled overlap case:

let overlap x y = match x, y with
  | 0 .. 10, true -> 1
  | 5 .. 15, _    -> 2
  | _ -> 0
(catch
   (if (isout 10 x) (exit 14) (if y 1 (exit 14)))
 with (14)
   (if (isout 10 (-5+ x)) 0 2))

Two chained tests: “x in 0..10 and y? → 1, otherwise exit”, and the handler tests 5..15 (as x−5 in 0..10). The fall-through edge is the exit 14 — first-match-wins is now a property of the structure, not of careful ordering.

7. Experiments to try

  1. Re-run every capture in this file (sections 2, 4, 5) — then vary them. Predict the Lambda before you look.
  2. Check out commit 3 (Produce Tpat_interval…), build, and compile an interval match: watch typing succeed, warnings work, and codegen fatal — the mid-series staging made visible.
  3. Make the exhaustiveness checker sweat: match x with -2147483648l .. 0l -> 1 | 1l .. 2147483647l -> 2 — no warning 8; then poke a one-value hole and watch the counter-example name it.
  4. Trigger the disjointness fatal_error in combine_constant_interval? You cannot — try to construct an overlap that reaches one dispatch, then read commit 9 to see why you failed.
  5. Diff git show of commit 9 against the extension-constructor comment in can_group (trunk code): same disease, same cure.
  6. Run the feature's own tests: make -C testsuite one DIR=tests/basic-more and DIR=tests/typing-warnings.

8. Glossary

TermMeaning
headThe outermost constructor of a pattern (Patterns.Head): a constant, an interval, Some, a tuple…
matrix / pmThe rows×columns view of a match's clauses; “pm” (pattern matching) is matching.ml's name for a matrix plus its actions.
specializationRestricting a matrix to the rows compatible with a given head, consuming the first column.
usefulnessRow q is useful w.r.t. matrix P if some value matches q and no row of P. Exhaustiveness and redundancy are both usefulness questions.
division / cellThe compiler's grouping of a matrix's rows by first-column head; each cell becomes one branch of a dispatch.
static exitLambda's catch … with (exit n) … / (exit n): a local, zero-cost goto used to chain match sub-matrices.
default matrixRows still relevant when the scrutinee's head is none of the dispatched ones; compiled as the exit handler.
disjointificationCutting a set of intervals at each other's bounds so any two pieces are equal or disjoint (parmatch's css).
first-match-winsOCaml's guarantee that the textually first matching clause is selected — the property both historical bugs violated.
